# Realtime response and input provenance — staged design

Status: **HOLD for integration and publication.** SDK and Harness worktrees are checkpoints. This document describes the scoped implementation and outstanding product protocol work, not a claim of live-provider, package, or device validation.

## Provider capability boundaries

OpenAI manual turns can attach an unpredictable host-generated tag to `response.create.response.metadata` and compare the returned `response.created.response.metadata` with the pending request. Bind the returned response ID once; require response/tool frames to carry that same ID until the raw `response.done` frame completes, reject unknown or reused IDs, and retain a bounded set of retired IDs to ignore late duplicate terminal projections. Each tool continuation receives a fresh tag. Local `InputSent` remains only a send-order marker. The ordinary tool permission, sandbox and cancellation paths still apply.

This associates a provider response and its tool frames with a host **response request**; it does not establish the exact input that the model semantically consumed or prove which locally captured audio produced an input transcript. On a response failure, terminate the operation visibly rather than report successful completion. Official protocol references: https://developers.openai.com/api/reference/resources/realtime/client-events#response.create and https://developers.openai.com/api/reference/resources/realtime/server-events#response.created .

OpenAI `input_audio_buffer.committed` supplies a server item ID but does not document an echo tying it to the client's particular `input_audio_buffer.commit`. A count of pending commits, local ordering, or receiving a transcript while a local turn is active is not that proof. See https://developers.openai.com/api/reference/resources/realtime/server-events#input_audio_buffer.committed . The existing `AudioInputAdmissions` checks are not provider-to-local-input attribution.

Gemini Live documents function-call IDs for matching function responses, but not a provider-supplied association of each call or transcription to a particular local input. Its `gemini-turn-*` and `gemini-input-*` codec identifiers are local synthetic state and must not be promoted into provider evidence. See https://ai.google.dev/api/live and https://ai.google.dev/gemini-api/docs/live-api/tools . For a tool proposal with no supported response correlation, require an independent, explicit one-shot human confirmation for the exact action and arguments; saved allow rules, default acceptance, classifier approval and no-op gates cannot stand in for this confirmation. Apply the ordinary tool policy and sandbox after confirmation. Confirmation authorizes that proposed action only; it is not evidence of audio, transcript or user-input provenance. A host without interactive confirmation fails closed with a visible error. This fallback is not yet a complete product-facing solution until its provenance is communicated in the client.

## Required App and wire follow-up

The proposed fields need coordinated implementation and tests; they are not present in the current App and no App source was modified here:

- Add a source assurance field, for example `originAssurance: "provider_response" | "session_unattributed"`, to the internal realtime event and the JSON emitted by `apps/audio-provider/src/realtime.rs::canonical_agent_event/canonical_event`. Use `provider_response` only for a verified response binding. Input transcription without a demonstrated local-input link and Gemini audio/transcription without a provider correlation remain `session_unattributed`; omit inferred `turnId` for them. Preserve playable audio and transcript content, explicitly scoped to the session.
- Inspect each downstream path for chronological/current-turn fallback that would silently recreate a false association. Minimum desktop consumer: `apps/electron/src/main/audio/realtimeAudioController.ts` handles `audio_delta`; `apps/electron/src/main/bridge.ts` forwards `realtime_audio_event`. Product history persistence also needs an explicit session-level origin instead of appending an unattributed transcript as evidence for the current input. Audit mobile and other consumers before enabling the feature.
- Extend Harness `crates/client/src/protocol/permission.rs::PermissionRequest` and generated clients with a distinct origin field such as `originAssurance: "unattributed_realtime"`; `apps/electron/src/renderer/components/PermissionPrompt.tsx::describe` should show a localized explanation such as “无法确认此请求属于当前输入，是否仍执行此操作？”. Preserve the exact tool name and full arguments, deny-by-default, one-shot-only choice, and ordinary permission/sandbox checks. Require the current client contract to present that reason; a host without the complete confirmation capability must fail closed for this mode. The App currently maps most Harness failures to the generic `native Agent session failed` in `apps/audio-provider/src/realtime.rs`; propagate a structured confirmation-unavailable or confirmation-denied error and show its localized reason before claiming the restriction is user-visible.
- Add regression tests for missing/unknown provenance, stale late output, session-level playback/transcript placement, confirmation UI, rejected/expired/cancelled prompts, and no silent attribution by current-turn fallback. Confirm the same behavior on all supported clients.

The exact field names are proposals, not a published contract. The App and history/transport changes require their own scoped implementation and verification before a release claim. The pre-existing App pin points to commits not verified publicly retrievable; do not publish dependent checkpoints merely to make that pin resolve.
