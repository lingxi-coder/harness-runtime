## Final source follow-up on 4311d2be…

Re-read the complete candidate diff, stream acquisition/free and the source branches `ca_snapshot_create`, `ca_snapshot_clone`, and `git_mbedtls__set_cert_location`. The setter builds a private candidate before taking the publication lock; file failure prevents path parsing, all detected nonzero results reject the candidate, and a specified source must leave a parsed certificate with nonzero `version`, non-null DER and nonzero length. Only after those checks does it exchange `current_ca`; an unsuccessful candidate or failed publication lock is freed without replacing it. A caller that began cloning before the exchange pins the template until all DER reads are complete. Every stream then has a distinct chain and public-key contexts, and the SSL object is freed before that stream's copy is released. This addresses the earlier identified CA lifetime, empty-chain/OOM-check and combined file/directory errors at source level. No additional blocker was found in the reviewed candidate under the lifecycle and filesystem limits stated in this report; it is not a whole-backend safety approval.

The positive parse result now formats as a skipped-entry count; negative errors go through `mbedtls_strerror` and pass `(unsigned int)ret` to `%#04x` (`streams/mbedtls.c:101-108`), fixing the prior signed/unsigned variadic-format mismatch in this new branch. Existing older `ssl_set_error` formatting is outside that specific correction.

The author reports successful native tests. I did not run them. The four retained `ca-snapshot/real-tls-fresh-{rsa,ec}-{address,thread}.log` files contain TLS 1.2/1.3 good-host and wrong-host PASS lines with concurrent CA update counts; `real-tls-fresh-inputs.json` records their compilation inputs. The generated `real-tls-snapshot.c` contains the candidate CA global/helper/init and setter bodies, with the final source differing there only by the explicit error-format cast and whitespace; it supplies stubbed libgit2 atomic/error functions and calls snapshot acquisition plus Mbed TLS setup directly, rather than compiling the complete libgit2 stream wrapper. I independently observed ThreadSanitizer symbol references in all three `final-tsan` Mbed TLS archives; I found no AddressSanitizer symbol references in the three `final-host` archives used by the ASan harness, so the ASan result must not be characterized as full native-library instrumentation. `snapshot-final-{address,thread}.log` each report one passing test; those logs alone do not establish the precise source digest or real-device behavior. No test output establishes Android certificate-store compatibility, full application behavior or all possible concurrent interleavings.

## Follow-up on e1254d1c…

The author changed the policy after the f319d6e8… finding below. The e1254d1c… candidate rejects any nonzero file/path parse result and checks `version`, `raw.p`, and `raw.len` before publishing an explicitly configured trust set (`streams/mbedtls.c:96-109`). This addresses the described first-DER-allocation failure and ordinary empty/all-invalid directory cases. A transient 8ea68096… version accepted both `file` and `path` but could overwrite a positive file parse result with a successful directory result. The e1254d1c… candidate invokes the directory parser only if the file result is exactly zero, addressing that combined-input error path as well.

This strict policy intentionally changes the earlier permissive behavior: a directory with at least one valid certificate and one unparseable or unreadable regular file is now rejected as a whole. Whether all real Android system CA directories are compatible has not been established by this reviewer. Upstream `x509_crt.c:1619-1655` does not check `errno` after `readdir` returns NULL and skips `stat` ENOENT; a zero return therefore cannot guarantee an atomic, complete view if the directory itself changes or enumeration fails. The candidate preserves the previous snapshot for **detected** nonzero parser results; it cannot by itself guarantee detection of every filesystem enumeration failure. No new blocking defect was identified in these specific updated branches from source reading, subject to those limits and independent runtime testing.

## Historical blocking finding in f319d6e8…: an allocation failure could bypass the empty-chain guard

The revised candidate rejects an explicitly supplied file/path if `snapshot->ca_chain.raw.len == 0` (`streams/mbedtls.c:96-109`), which addresses ordinary empty or all-invalid directories. That is not a reliable successful-parse indicator under allocation failure. In upstream `x509_crt.c:1118-1124`, DER parsing assigns `crt->raw.len` **before** allocating `crt->raw.p`; failure returns `MBEDTLS_ERR_X509_ALLOC_FAILED` immediately, leaving a nonzero length, null pointer, and zero `version`. `mbedtls_x509_crt_parse_der_internal` leaves the failed first node in place (`:1335-1365`). When this failure comes from a directory entry, `mbedtls_x509_crt_parse_path` counts a negative per-file parse result and can return a positive total (`:1646-1653`), which the candidate accepts. A directory where no certificate succeeds but the first certificate's DER allocation fails can therefore pass the `raw.len` guard, be published, and replace the last working template while the setter returns success. A later per-stream clone tries to parse the null raw pointer and fails (`streams/mbedtls.c:129-135`; upstream `x509_crt.c:1328-1333`).

This is a conditional, source-proven error path, **not dynamically reproduced** or shown to affect an actual device. It is an availability / false-success failure, not a demonstrated trust bypass. A correct condition must establish at least one successfully parsed certificate, including in this partial-allocation state. The product's `crates/tools/git-mobile/src/auth.rs:422-459` documents that a directory from which no valid cert can be parsed should produce an error, so the distinction is material to a real direct caller.

The earlier policy accepted positive `parse_path` results, which collapse a negative result for an individual file into a positive count; malformed files, per-file I/O errors, and resource failures are indistinguishable at that API boundary. The later strict e1254d1c… branch rejects these detected partial results instead. No claim is made that historical partial-directory acceptance was newly introduced or itself a demonstrated security bypass.

## Changes that address the earlier review findings

- In bbbd3171…, all streams pointed at the same parsed CA public-key contexts. With `MBEDTLS_USE_PSA_CRYPTO` disabled by this configuration, X.509 parent signature verification can reach the same ECDSA context via `x509_crt.c:2174` → `pk.c:1221,1180` → `pk_wrap.c:1130-1136,688-696` → `ecdsa.c:743-744` → ECP multiplication. Upstream `ecdsa.h:56-68` and `ecp.h:1016-1020` do not support concurrent operations on one such context/group. This was a source-contract problem; a real data race was **not** established. The default 3.6.7 built-in curves load static precomputed tables (`ecp_curves.c:4518-4547`) so the dynamic write in `ecp.c:2339-2340` does not automatically prove a race for those curves.
- In f319d6e8…, a stream instead parses each certificate's encoded bytes into its own chain/config (`streams/mbedtls.c:118-145`). Upstream `mbedtls_x509_crt_parse_der` passes `make_copy=1` (`x509_crt.c:1388-1393`) and allocates/copies the raw bytes (`:1118-1128`); the published template's certificate/key object is not passed to `mbedtls_ssl_setup`. This source design addresses the identified shared-ECDSA-context contract issue, subject to actual concurrency/handshake tests and other global limitations below.
- The first clone implementation passed the head to the DER append helper for every certificate, causing quadratic chain traversal. The f319d6e8… version passes `tail` and advances to the new node, so the append traversal is linear in chain length (`streams/mbedtls.c:122-140`; `x509_crt.c:1335-1353`). Each stream still pays for a full parse and separately allocated chain. Actual connection latency, memory and Android CA-store cost have not been measured by this reviewer.

## Lifecycle and concurrency assessment

With the documented libgit2 lifetime rule respected, the published template owns one reference. An acquisition increments it while holding `ca_lock`, then clones outside the lock and drops the pin; a concurrent setter swaps the pointer while holding the same lock and releases the prior template after unlocking. Thus replacement cannot free a template while an acquiring stream is copying it. Each successful clone starts with its own reference and is handed to only one stream; `mbedtls_ssl_setup` retains its config pointer (`ssl_tls.c:1384-1395`, documented in `ssl.h:2062-2070`). Setup failure, host-allocation failure and normal free release the SSL context before the stream's clone. A failed clone frees its partially built copy, and the template pin is released after either clone outcome. This reasoning assumes normal mutex operation, successful runtime initialization, and no concurrent access to an individual stream beyond its API contract; it is not a dynamic proof.

Each stream binds the snapshot when its wrapper is created, not when its later handshake begins. A setter can therefore return while an already-created but not-yet-connected stream retains the old trust set. Concurrent setters are ordered by publication, not by the time they started parsing. A certificate parse failure or publication-lock failure with a negative result discards the candidate and retains the previous published template.

`shutdown_ssl` does not take `ca_lock`; it releases the global template, frees the shared RNG/entropy and destroys the mutex (`streams/mbedtls.c:178-191` in e1254d1c…). The design relies on libgit2's documented requirement that worker threads finish before final `git_libgit2_shutdown` (`libgit2/README.md:190-204`). The per-stream CA copy alone does not make it safe to use a stream, start a setter, or reinitialize after final shutdown while an old stream still runs: configs also reference static `ciphers_list` and `mbedtls_rng`. The git2 Rust wrapper intentionally keeps its runtime initialized for process lifetime (`libgit2-sys/lib.rs:4721-4734`). These do not prove all possible C callers observe the contract.

Normal last shutdown followed by a new init reinitializes the mutex, cipher list and RNG, subject to no remaining callers/streams. A separate **pre-existing** libgit2 failure-retry issue remains: `runtime.c:119-121` increments `init_count` before running initialization but does not undo it if `init_common` fails. A later C init call without an intervening shutdown may return a positive count without rerunning TLS initialization, even though this candidate cleaned up its mutex/RNG. The e1254d1c… version guards subsequent CA acquisition and setting with `ca_lock_initialized`; that guard does not make the reported retry initialization successful, nor does it make concurrent final shutdown supported. The Rust Once wrapper panics on initialization error; a product retry path was not established. A successful shutdown/reinit test does not establish the failure/retry path.

## Shared Mbed TLS global boundaries

`mbedtls_ssl_config_defaults` calls `mbedtls_ssl_list_ciphersuites` (`ssl_tls.c:6123-6125`); in this build the latter lazily writes static `supported_init` and `supported_ciphersuites` without its own synchronization (`ssl_ciphersuites.c:1800-1838`). Candidate global init primes this path before its own subsequent concurrent clone/setter calls. That reasoning does not prove serialization against every other independent consumer of the same Mbed TLS library during first initialization.

The shared backend RNG is seeded once and each config references it; on Unix/Android the LingXi config enables Mbed TLS threading, and `ctr_drbg.c:696-714` locks around random generation. The wrapper does not enable Mbed TLS threading on Windows, but this libgit2 build selects WinHTTP there and Secure Transport on Apple (`libgit2-sys/build.rs:251-260`); claims for other Mbed TLS consumers or custom backend selections require separate assessment. The separately recorded post-fork PSA RNG synchronization candidate in `native-source-review.md` is not resolved by this CA snapshot change.
