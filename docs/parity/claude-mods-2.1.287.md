# Claude Code Mods 2.1.287 parity ledger

Reference version: `@anthropic-ai/claude-code@2.1.287` (October 1, 2026). The public contract is [Mods reference](https://code.claude.com/docs/en/plugins/mods/reference) and its linked `mods/types/claude-code.d.ts`. The available local declaration snapshot is stamped 2.1.277, so its API shapes still need checking against a 2.1.287 declaration. The 2.1.287 darwin-arm64 executable used here reports `2.1.287 (Claude Code)` and has SHA-256 `6eab8333fe2121553100d8f40bfada384a3e989b94f947e18ba6677a6fcb41ea`. It was used to compare `claude plugin validate --json` for module count, relative paths, extensions, missing files, and path escapes; a separate fixture confirms that it accepts the `clock.now/sleep/after/every`, `session.cwd/root/model/id/turns/repo/version/messages/surfaces/surface`, `fs.read/write/exists/list/stat/ancestors`, `store.get/set/delete/keys`, `state.get/set`, `env.get/set`, and `process.run`, `model.fork`, `model.complete`, and `model.classify` events, `fs.*` and `!tool.call` patterns, and their matching `$` calls. Its `claude plugin test` reports the rollout switch off on this machine even with `CLAUDE_CODE_ENABLE_FUNCTION_HOOKS=1`; runtime bytes cannot yet be oracle checked.

LingXi keeps its product manifest at `.lingxi-plugin/plugin.json`; Claude Code uses `.claude-plugin/plugin.json`. This is an intentional brand path difference, so a Claude plugin needs that manifest directory adapted before LingXi discovers it.

The static API-name fixture is `docs/parity/fixtures/claude-mods-2.1.287-api`. Recheck it with a 2.1.287 binary using `claude plugin validate --json docs/parity/fixtures/claude-mods-2.1.287-api`; this validates names and source scanning, including `plugin.register`, `prompt.context`, `session.end`, `tool.check`, `tool.list`, `tool.register`, `command.list/register/run`, `env.get/set`, `ui.log`, `ui.toast`, `ui.status`, `ui.invalidate`, `prompt.section`, and `prompt.compose`, not runtime behavior.

Do not advertise full Claude Code Mod compatibility from this branch yet. The Mod result stage protects the ordinary `toolUseResult` side table and tool-result SDK frame from the superseded core result. Tool implementations and classic hooks can still produce independent side effects, and the current implementation cannot guarantee that a Mod's replacement redacts every log, sidecar file, attachment, or UI progress event. `$.ui.log` renders as a separate dim Mod row, but exact upstream transcript persistence is not verified.

Desktop Mod evaluation is gated on the host's workspace-trust decision. If trust changes from false to true during a session, a plugin refresh is required to load previously skipped modules.
