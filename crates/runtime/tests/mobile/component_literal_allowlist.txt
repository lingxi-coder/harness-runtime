# component_literal_allowlist.txt — P-1.0
#
# One explicit `path:literal:expected_count` entry per PERMITTED (path,
# literal) pair — an occurrence of a Local App component (skill / workflow)
# name as a literal in PRODUCTION source. `path` is relative to the cargo
# workspace root (`lingxi-code/`), matched by EXACT string equality; so is
# `literal`. No globs, no directory entries, no prefixes.
#
# Scan surface (component_literal_scan.rs's SCAN_ROOTS):
#   runtime/src/mobile, tasks/src, tools/workflow/src, workflow/src, local-app-service/src
# — `tools/workflow/src` and `workflow/src` because design doc §19.3's last bullet and P-1.9's
# completion condition are stated over exactly those directories, so a scanner
# rooted only at the mobile host could never gate them; `local-app-service/src`
# because the Local App broker, build pipeline and MCP server live there now.
#
# Within those roots EVERY file type is scanned except the known-binary
# extensions in SKIPPED_EXTENSIONS: the filter is a deny-list, so an unknown
# extension is scanned rather than skipped. That is why `.txt` and `.json` under
# workflow/src (`workflow_description.txt`, the Workflow tool's own
# model-facing description, and `workflow_input_schema.json` — both
# `include_str!`ed into production) are in the scan surface. Neither contains a
# component name today, so neither appears below; if a later phase moves
# workflow-selection prose out of an allowlisted `.js` script and into the
# description text, the arrival now shows up here as a LEAK rather than only the
# departure showing up as a STALE ENTRY.
#
# ## Why entries are NOT keyed on line numbers
#
# They used to be, and that made every unrelated edit above an allowlisted
# line produce a spurious "leak" whose cheapest fix is re-typing line numbers
# with the count unchanged — the re-baseline reflex this gate exists to
# prevent. P-1.2/P-1.4 edit the Host broker (now local-app-service/src/broker.rs), P-1.3 edits
# workflow_support.rs, P-1.5 edits lib.rs; all of them would have paid it.
# The FAILURE OUTPUT is still line-numbered ("name the file and the line" is a
# requirement on what the gate says, not on how the allowlist is keyed).
#
# ## Why every entry carries a COUNT, and why the count is EXACT
#
# - Without a count, ONE entry covers unlimited same-file occurrences of that
#   literal — including new ones added later.
# - Without exactness in the DOWNWARD direction, the allowlist is a permitted
#   superset: deleting the code an entry points at, or dropping a file out of
#   the directory walk, leaves the gate green with a standing pre-approved
#   hole behind it. component_literal_scan.rs's
#   `every_allowlist_entry_still_matches_a_real_occurrence` and its
#   COUNT MISMATCH finding close both directions.
#
# The NUMBER OF ENTRIES is pinned separately by ALLOWLIST_BASELINE_COUNT
# (`allowlist_entry_count_matches_the_committed_baseline`), so replacing
# several precise lines with one broad one still has to explain, in the same
# diff, why the committed count moved.
#
# Phase -1 deliberately KEEPS the two pre-existing Local App workflow
# registrations (tools/workflow/src/builtins.rs plus the three .js files it
# include_str!s) and the skill-name mirror `register_mobile_skill_commands`
# duplicates into the slash-command catalog, so this file cannot be empty
# today, by design — Phase 9 is expected to drive it to zero.
#
# `#[cfg(test)]` regions — inline blocks AND out-of-line test modules such as
# `tasks/src/registry_test.rs` and `tasks/src/handlers/local_workflow_test.rs`
# — are skipped by the scanner and therefore appear nowhere below.

# local-app-service/src/broker.rs (was runtime/src/mobile/local_apps_host.rs) — P-1.4 removed the Host's two prose sentences naming
# which build workflow the app's surface requires (§19.3: the Host contract
# carries no workflow/skill/agent names). The Host still selects and enforces
# the build WORKFLOW itself via LocalAppPluginBinding::resolve/enforce
# (local_app_plugin_binding.rs, below); no workflow id appears in this file.
#
# WP8 (2026-09-02 create-flow audit) reintroduces a narrower, deliberate
# exception for the SKILL name only: the guided workspace contract
# (`guided_workspace_contract`) and the empty-shell handoff prose
# (`create_next_step_guidance`) both point the model at the `create-local-app`
# skill for the next step, because there is NO host-initiated launch site for
# the create build workflow (the host only auto-starts MCP authoring and
# resume) — the model can only continue create by name, and the model is
# already only in this workspace because it ran that skill once already, to
# create the shell. This does not reopen P-1.4: the WORKFLOW the skill goes
# on to launch is still resolved entirely inside the skill/workflow layer and
# still appears nowhere in this file.
#
# The literal is the PLUGIN-QUALIFIED name `lingxi-local-app:create-local-app`,
# not the bare skill name: plugin skills are registered only as
# `<plugin>:<skill>` (`plugin/src/manager.rs`), and the Skill tool's mobile
# loader resolves through `CommandRegistry::resolve`, an exact-match lookup with
# no bare-name fallback (the bare->qualified retry in
# `skill_loader.rs::resolve_agent_skill_name` serves agent-frontmatter
# preloading, NOT the tool). Host prose naming the bare form would send the
# model to `Unknown skill: create-local-app`.
#
# The on-demand testing hand-off prose names the two plugin test SKILLS so the
# model can invoke them: testing is never host-initiated, so the only way to
# reach the app's on-device use-test path is by name.

# host.rs — the ONE place the three plugin-owned entry routers are kept visible
# in a global/project conversation. Every other `lingxi-local-app:` skill is
# hidden outside an app workspace, so this filter needs the names of exactly
# the skills that stay: it is a membership test on `c.name`, i.e. the literal
# IS the datum, and there is no registry to ask (the plugin inventory carries
# no "is an entry router" flag). Same qualified-form reason as the entries
# below: `CommandRegistry` keys plugin skills as `<plugin>:<skill>` with no
# bare-name fallback, so a bare literal here would match nothing and silently
# hide all three routers instead of showing them.
runtime/src/mobile/host.rs:lingxi-local-app:create-local-app:1
runtime/src/mobile/host.rs:lingxi-local-app:expose-as-mcp:1
runtime/src/mobile/host.rs:lingxi-local-app:local-app-use:1

#
# `local-app-build` is KEPT: the unified CREATE launch retired with the
# plan-driven `LocalAppPrepare` flow, but the same identity still gates the
# named/scriptPath UPDATE and VERIFY resumes
# (`apply_materialized_local_app_collections_with_identity` +
# `persisted_workflow_script_path`), so the const and its binding stay in
# production.
runtime/src/mobile/local_app_plugin_binding.rs:lingxi-local-app:local-app-build:1
runtime/src/mobile/local_app_plugin_binding.rs:lingxi-local-app:local-app-mcp-authoring:1
runtime/src/mobile/local_app_plugin_binding.rs:lingxi-local-app:local-app-use-test:1

# workflow_description_divergences.json — the register of named divergences
# from the byte-locked oracle Workflow description. This is exactly the arrival
# this file's own header (see "if a later phase moves workflow-selection prose
# out of an allowlisted `.js` script and into the description text") said would
# show up here as a LEAK rather than going unnoticed, so it is listed rather
# than reworded.
#
# Two of the three occurrences are in the `text` of the `local-app-create-handoff`
# divergence and in the `reason` that justifies it. `text` is the sixth opt-in
# clause composed into the description the model actually reads: the oracle's
# five clauses are exhaustive and closed with "For any other task ... do NOT
# call this tool", so without a clause naming the flow, every create is a call
# the model is told not to make. The clause has to name the skill the Host
# contract hands off to, and it has to name the PLUGIN-QUALIFIED form for the
# same reason as the `runtime/src/mobile` entries above.
#
# The third is the bare basename inside the repository PATH
# `skills/create-local-app/SKILL.md`, cited in that same `reason`. `reason` is
# never composed into the shipped description — only `anchor` and `text` are
# (`compose_description` in tools/workflow/src/lib.rs) — so this occurrence is
# not model-facing at all; it is a pointer to the file a reader has to open to
# check the claim. There is no rewording that keeps a real path and drops the
# basename, so it is listed here instead of being paraphrased away.
workflow/src/workflow_description_divergences.json:create-local-app:1
workflow/src/workflow_description_divergences.json:lingxi-local-app:create-local-app:2
