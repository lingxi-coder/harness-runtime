## 1. Cron — one item, blocked on hardware

### 1.1 Real-device QA has never been run

The mobile promise is "set a scheduled task, and have the device wake and run
it". That is verified as far as a host can take it and **no further**:

- iOS: 658 tests on the simulator, against the rebuilt `LingxiCodeFFI.xcframework`
- Android: 793 unit tests + a clean Kotlin compile, against the regenerated binding
- Engine: `engine-mobile` 722 with `--all-features` (the uniffi-gated paths)

None of that exercises `BGProcessingTaskRequest` or `AlarmManager`. The wake
paths are confirmed by code walk only: Info.plist identifier, the five re-arm
sites, `AlarmManager.setExactAndAllowWhileIdle` → `CronAlarmReceiver` →
`CronDispatchWorker` → `CronExecutionWorker`, the 15-minute watchdog, and the
boot / time-change receivers.

**Why it did not run:** the paired iPhone 11 is **wireless** (`devicectl` shows
`panggedeiPhone.coredevice.local`, `available (paired)`). `xcodebuild test
-destination "platform=iOS,id=00008030-001549902184802E"` fails with
`Timed out waiting for all destinations matching the provided destination
specifier to become available`. This matches the existing note that real-device
XCUITest is blocked with DTX `code 74` and that wireless transport was the one
cause never excluded — but the **unit-test bundle is known to work on device**,
so this is not the same wall.

**To finish it:** connect the iPhone over USB, unlock it, then

```
xcodebuild test -project clients/ios/LingxiCode.xcodeproj -scheme LingxiCode \
  -configuration FullDebug -destination "platform=iOS,id=<device-udid>" \
  -only-testing:LingxiCodeTests/CronRepositoryTests \
  -only-testing:LingxiCodeTests/CronLifecycleTests \
  -testLanguage zh-Hans -allowProvisioningUpdates
```

Android needs a device attached at all (`adb devices` was empty), then the
instrumented suite.

⚠️ The thing a device run is actually for is the class of bug a simulator
cannot show: the OS declining to wake, the wake arriving far late, the app
being killed mid-execution. Passing unit tests on device is necessary, not
sufficient — watch a real scheduled task fire with the app backgrounded.

### 1.2 Not tasks — decided, do not "fix"

Recorded here so nobody reopens them:

- **Three knowingly-not-aligned**: scheduler-lock ownership arbitration (LingXi's
  per-job claim lock is a superset and `sessionId` already means something else
  in the Desktop feature); mobile executes a late one-shot instead of surfacing
  it (the OS wake *is* the scheduled moment, and a confirmation turn would mean
  scheduled tasks never run unattended); `permanent` is not exempt from the
  recurring age check (unreachable — no global recurring age exists).
- **Two accepted divergences** (user decision, 2026-09-07): no global 7-day
  expiry, per-task `expiresAt` instead; `expiresAt` / `sessionId` are not oracle
  fields.
- **One not applicable**: CronCreate's teammate `agentId` / `shouldDefer` /
  `getPath` — the teammate subsystem does not exist here.

Full reasoning: `lingxi-code/docs/cron-parity-audit-2026-09-06.md`.

### 2.1 A user-initiated stop now tells the model nothing

`tasks/src/registry.rs` — `stamp_kill_notified` (`:4441`), called from
`mark_killed` (`:4278`).

The kill-notification suppression is keyed on task **type**, and justified by
"a model that called TaskStop already has `Successfully stopped task: X` in
hand". That holds for two of the five `kill_with_reason` call sites. The other
three are user-initiated — the TUI `/tasks` picker (`apps/cli/src/mode.rs`,
reason `"user"`), the desktop task panel (`apps/bridge-server/src/router.rs`)
and the SDK control channel (`apps/cli/src/run.rs`) — and deliver only a UI
event. The drain gate is `terminal && !notified`, so after the stamp the model
receives nothing and keeps waiting on a dead command.

`registry.rs:1125` states the opposite invariant in prose: *"this is the
opposite of a user-initiated `TaskStop`, where the stop notification is the
point"*. `killed_by` is already threaded into `kill_with_reason` and is the
origin signal this decision should read instead of the task type.

### 2.2 A killed armed foreground row is never withdrawn

`tasks/src/registry.rs` — `unregister_foreground_bash` (`:1313`).

It treats `notified` as a leave-this-row-alone flag
(`if bash.is_backgrounded == Some(true) || bash.base.notified { return; }`), so
once a killed foreground row carries the new stamp, `ForegroundArming::disarm`
declines to remove it. Nothing else evicts terminal rows —
`evict_terminal_tasks` is a deprecated no-op — so a `Killed` row accumulates in
TaskList and the not-found rosters for the rest of the session. `disarm`'s own
doc says withdrawing "is not optional".

### 2.3 A shell whose sink flipped it first gets no `[killed]` trailer

`tasks/src/registry.rs` — the terminal branch of `mark_killed`.

`LocalBashHandler::kill` sets `Killed` through its sink before `mark_killed`
runs, so `append_killed_trailer` is a no-op and `settle_background_bash` also
early-returns on a terminal row. A later `Read` of the spool shows output
stopping mid-stream with no marker — the claude-code parity behaviour
(`JF`: `s1e(e, "\n[killed]\n")`) the trailer exists to port. The trailer test
uses the Running→kill shape, the one case that *does* write it, so the suite is
structurally blind to this.

### 2.4 A registry-only kill fires no `TaskCompleted` hook

`tasks/src/registry.rs` — `mark_killed` writes status via `base_mut()` rather
than `set_status`, so `fire_task_completed_hook` never runs for a task with no
`spawned` entry (e.g. a Bash-tool background shell registered via
`register_background_bash`). A user-configured task-completed hook never
observes a stopped shell. This is the hook/event channel, distinct from 2.1.

## 3. Open review findings — `tasks/src/output_manager.rs` (owner: its author)

### 3.1 The 5 GB cap counts UTF-16 units under a byte-named constant

`output_manager.rs:17` `MAX_TASK_OUTPUT_BYTES = 5 * 1024 * 1024 * 1024`.

The accumulator was changed from UTF-8 bytes to UTF-16 code units. **That is
faithful** — verified at the oracle (2.1.263 @159592930):
`append(t){ this.#f += t.length; if(this.#f > r1e) this.#o = true; }` with
`r1e = 5368709120` and the marker text `"5GB"`. JS really does count UTF-16
units against a byte-named cap.

The consequence is real regardless: a task spooling CJK passes 5 GB **on disk**
at ~1.7 G units and reaches ~15 GB before the marker fires (emoji ~10 GB) — on a
volume that has repeatedly run to single-digit GiB free. Meanwhile the constant
name, `bytes_written`, the `append` doc ("per-file 5GB disk cap … on the WRITE
side"), `validate_terminal_result` (still `content.len()`, i.e. bytes) and the
neighbouring test's comments all still say bytes, and that test's `"ab"` fixture
is ASCII so it passes identically under either accounting.

**Decision needed:** keep oracle parity and rename/redocument, or keep the disk
ceiling and diverge deliberately. Either way the file should not say two things.

### 3.2 `OutputOptions.offset` / `.limit` are documented in bytes, applied in lines

`output_manager.rs:212` *"Byte offset to start reading from"*, `:214`
*"Maximum number of bytes to return"*. `read` forwards both to
`platform_api::apply_line_window`, which skips and takes **lines**.

`TaskRegistry::task_output(id, offset)` forwards a caller-supplied `offset`
straight through, so a caller following the documented contract (resume a poll
at the byte count already consumed) skips that many *lines* and gets an empty
tail while `truncated` reports the read complete. Every construction in the tree
passes `None`, so nothing pins the real semantics.

## 6. One unverified edge

`3a362177b` added a `was_live` guard so a task that settled **on its own** keeps
the kill notification it has not drained yet (a shell that hits its own timeout
also settles as `Killed`). The characterization test for that case failed with an
empty drain, and it could not be determined whether the guard was wrong or the
premise was — a settled task may already have been notified through the
completion path, which would make an empty drain correct.

The reasoning says premise: `was_live` can only ever *prevent* a stamp, so it
cannot cause an extra drain to go missing. **That is reasoning, not evidence.**
The test was removed rather than left red or forced green. If you touch this
path, prove that edge first.

## 7. Traps worth knowing before you touch any of this

- **The orchestrator has TWO turn loops, and THREE public entries.**
  `turn_loop::execute_one_turn` is the batched model step; `StreamingTurnDriver::run`
  (`conversation/drivers/mod.rs`) is the streaming loop, and **that is the one
  `bridge-server` drives** — desktop and mobile. The entries are `run_turn`,
  `run_turn_with_cancel` and `run_turn_streaming`. A branch added to one is dead
  on the others, and `cargo check` plus unit tests will not tell you. This cost
  two defects in `6fe69dd4f`, both fixed in `d231dd6ab`, and a third in
  `f5b38eade` where a shared reminder collector left its anti-drift guard red.

  The unified-driver series (`docs/unified-conversation-driver-plan-2026-09-15.md`,
  tags `ucd-p1`…) has since pulled the per-turn work into shared pieces, so
  "add it to both loops" is now usually "add it to one place":

  | shared | where | production call sites |
  |---|---|---|
  | per-turn reminders | `drivers/prepare.rs` `collect_turn_reminders` | 1 |
  | turn preparation (15 steps) | `drivers/prepare.rs` `prepare_turn_step` | 2 — one per driver |
  | prompt snapshot | inside `prepare_turn_step` | 1 |
  | loop state + output-token baseline | `drivers/loop_state.rs` `TurnLoopState::new` | 1 |
  | top-of-loop guards | `drivers/loop_state.rs` `run_turn_loop_guards` | 3 — one per entry |
  | end-of-turn sequence (Stop hooks → budget → emit) | `drivers/disposition.rs` `end_of_turn_sequence` | 3 — one per entry |
  | EndConversation consume | `drivers/disposition.rs` | 2 — one per driver |

  All three loops now have the same outer shape — guards, one round, a match on
  what it returned (`StepExit` / `TurnEndVerdict`) — so a change to what happens
  at the END of a turn (Stop hooks, the budget, the end event) is one edit
  instead of three. What the three still do separately is NAME the result, and
  the model step itself is still batched-vs-streaming.

  What is deliberately NOT shared, because the entries genuinely differ and the
  plan's §3.2/§3.5/§3.6 keep the differences: the top-of-loop guard ORDER (the
  cancelable entry does not drain; streaming checks cancel last), cancel
  handling, the NAMING of every terminal (the same verdict is an `Err` on one
  entry and an `Ok` on another), and the file-history epilogue, which only
  streaming has. Each is pinned by a cross-entry test that asserts the
  DIFFERENCE, so a "tidy-up" that makes two entries agree turns one red rather
  than passing quietly.
- **Between-turn events are dropped.** `FrameEventSink::emit` discards any
  `is_owned_turn_event` — `SystemNotice` included — that no active turn owns.
  Anything announced between turns needs the unscoped sink
  (`Connection::loop_wakeup_event_sink()`). Gate it with a unit test asserting
  `!is_owned_turn_event(&YourEvent)`.
- **This checkout is shared.** Several sessions write it concurrently. HEAD moved
  ~30 commits during this work, one session's `git add -A` swept an in-flight
  change of mine into `3537e08cf`, and a review agent's edit was clobbered
  mid-review. Stage per path, never `-A`; check `git status` before and after.
- **Disk.** `lingxi-code/target` is ~168 GB and shared by every session — do not
  delete it. Free space instead from `~/.npm/_cacache` (was 55 GB, pure download
  cache), Xcode DerivedData, or `xcrun simctl delete unavailable`. For your own
  builds set `CARGO_TARGET_DIR` to a scratch path: it sidesteps the build lock
  entirely (40-minute waits observed) at ~12 GB, and delete it when done.
- **`.git` is now 186 MB** (was 5.7 GB). 15 salvageable dangling commits are
  pinned under `refs/archive/dangling-2026-09-08/`; everything else pruned was a
  duplicate or a dropped stash. `git gc --prune=<date>` with a short-but-nonzero
  grace (`2.hours.ago`) is safe under concurrency; `--prune=now` is not.
